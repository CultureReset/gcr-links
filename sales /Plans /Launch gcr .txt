Based on everything I've seen across all 3 repos, here are my recommendations — ordered by impact:

🔴 Critical — Do These First
1. Write the card-rendering JS for category pages
This is the single biggest gap. Every listing page is a shell with no content. You need one reusable function that:
	•	Listens for gcr:loaded
	•	Reads data-category from the grid div
	•	Loops GCR.businesses, filters by subtype
	•	Renders a card for each: hero image, emoji, name, subtitle, rating, link to profile.html?id=slug
One ~100 line JS block handles all 8 pages. Without this, the site is functionally empty.
2. Wire up the filter chips
The HTML already has data-filter on every chip. There's just no logic behind them. After cards render, add a click handler that compares the filter value against each entity's tags[] array and shows/hides cards. Very small amount of code, makes the site feel alive.
3. Verify data is actually in Supabase
Before any frontend work matters — confirm entities exist in the GCR DB with at minimum: slug, name, hero_image_url, entity_subtype, city. If the DB is empty or sparse, the site will still look blank even after the JS is fixed.

🟡 High Value — Do Before Soft Launch
4. Add a static JSON fallback in gcr-api.js
You have data/api-businesses.json (180KB) sitting in the repo but gcr-api.js never loads it. If the Vercel API is slow or cold-starts, the page loads empty. Add a fallback:

// if fetch fails or times out, load from /data/api-businesses.json
Makes the site resilient and fast on first load.
5. Homepage category tile counts
Right now the tiles on index3.html show static numbers. After gcr:loaded fires, replace them with GCR.businesses.filter(b => b.entity_subtype === 'restaurant').length. One line per tile. Makes it feel real.
6. Events & Specials pages
Same card-rendering problem as listings, but events have date/time data which makes them more valuable to show. GCR.events[] is already loaded — just need to render cards sorted by date.

🟢 Admin Dashboard Improvements
7. Finish the Cards and Reviews section editors
Right now both just say "coming soon." Reviews are arguably the most important section for user trust — author name, rating, text. Cards are used for packages/tickets. These two section types have full backend support already, just need the UI built in admin.html.
8. Add a "Preview on Site" button in Entity Editor
When editing an entity in the admin, there's no way to jump to how it looks on the public site. A simple button that opens launching-gcr.vercel.app/profile.html?id={slug} in a new tab would save a lot of back-and-forth.
9. Photo upload in gallery sections
The gallery section editor loads photos but upload UI is unclear/missing. Since hero images and gallery photos are the most visually impactful part of any profile, getting uploads working in the admin is important.

🔵 Architecture Recommendations
10. Use the static JSON files as your seed/cache strategy
Instead of always hitting the API cold, consider having a build step (or cron) that exports the DB to data/api-businesses.json and deploys it with the frontend. Fast first paint, API only needed for single-entity detail pages.
11. Add category field to entity or use subtype-to-category mapping
Right now entity_subtype is granular (e.g. dolphin_cruise, parasailing) but the listing pages filter by broad category (e.g. things-to-do). There's no clean mapping between them in the frontend code. You need either a category column on entity, or a hardcoded mapping object in gcr-api.js like:

const CATEGORY_MAP = {
  'things-to-do': ['parasailing', 'dolphin_cruise', 'kayak_rental', ...],
  'restaurants': ['restaurant', 'hybrid_venue', ...],
  ...
}
12. Slug-based URLs instead of ?id=
/profile.html?id=dockside-parasail works but /dockside-parasail or /place/dockside-parasail looks much cleaner and is better for SEO. Vercel's vercel.json supports rewrites — a small config change routes /place/* → /profile.html?id=*.

This is a strong platform vision. Let me give you honest, structured feedback on all of it.

The Core Idea — What You're Actually Building
You're not just building a tourism directory. You're building a local business operating system where:
	•	GCR is the public-facing discovery layer (tourist finds the business)
	•	CyberCheck dashboard is the business management layer (owner controls everything)
	•	SMS/automations are the revenue + retention layer (keeps businesses paying)
	•	Booking integration is the transaction layer (you make % per booking)
That's a real business. The pieces already exist — the question is how to connect them properly.

1. Multi-Category Data Display (Your First Question)
The problem: A restaurant that has happy hour, bingo, and live music should show up on the restaurants page, happy hour page, events page, and be searchable for all three.
The fix — tags drive everything:
Right now entity_subtype is a single value (e.g. restaurant). You need a multi-tag system where one entity can have many searchable attributes:

entity: "LuLu's Restaurant"
  entity_subtype: "restaurant"   ← primary category (determines main listing)
  entity_tags:
    - { tag: "happy_hour",   tag_category: "amenity" }
    - { tag: "live_music",   tag_category: "amenity" }
    - { tag: "bingo",        tag_category: "activity" }
    - { tag: "waterfront",   tag_category: "vibe" }
    - { tag: "seafood",      tag_category: "cuisine" }
    - { tag: "family_friendly", tag_category: "vibe" }
Your entity_tags table already supports this — it's already built. The gap is:
	1.	Frontend: Category pages need to query by tag, not just subtype. The happy hours page shows anyone with tag: "happy_hour". The events page shows anyone with tag: "live_music" or tag: "bingo".
	2.	Search: When a tourist searches "bingo near me" — hits the tags table, returns LuLu's even though it's a restaurant.
	3.	Profile page: If LuLu's has a grouped_items section with section_key: "happy_hour" — that tab appears automatically. Same for bingo schedule, live music calendar.
The pages become tag-filtered views, not category-filtered views. One entity appears everywhere it's relevant.

2. Photographers — Smart Revenue Target
This is smart. Photographers are:
	•	Already looking for local clients
	•	Underserved by existing platforms
	•	Natural cross-sell (they shoot your businesses, you host their profile, you sell them a website)
What a photographer profile needs on GCR:
	•	Portfolio gallery section (already supported — section_type: gallery)
	•	Pricing/packages section (grouped_items)
	•	Booking button (Book Now → your platform or their Calendly/FareHarbor)
	•	Tags: portrait, wedding, real_estate, aerial, underwater, etc.
They show up on a "Services" or "Local Pros" page filtered by tag. Tourist searches "beach photographer orange beach" — finds them. Photographer pays you for the listing + website + booking. That's 3 revenue streams from one client.

3. Booking Platform — The Right Approach
Your instinct to integrate with FareHarbor/Peek first is correct. Here's why:
	•	FareHarbor/Peek already have the operators — fishing charters, boat rentals, dolphin cruises — they trust these platforms for payment
	•	Don't compete with them yet — add a "Book Now" button that deeplinks to their FareHarbor/Peek listing
	•	You still control the discovery — tourist finds them on GCR, clicks Book Now, goes to FareHarbor. You're the top of the funnel.
	•	Later: offer your own booking as a cheaper alternative ("pay 3% instead of 6%") for businesses that want to switch
The integration work is minimal — just store fareharbor_id or peek_url on the entity and render a Book Now button that links out. You can charge for the listing placement regardless.
Where your booking platform wins: Things that FareHarbor doesn't do well — last-minute SMS promos, catch of the day updates, QR checkin, review collection. Those are your differentiators.

4. The SMS Tools — Highest ROI Features
These are genuinely valuable and underbuilt in the market. Prioritize:
Catch of the Day
	•	Morning SMS to fishing charter: "What did you catch today? [Snapper] [Grouper] [Flounder] [Other]"
	•	They tap one button
	•	GCR updates instantly: "Today's catch: Red Snapper ✅" visible on their profile + feeds
	•	Tourists see real-time info → more bookings
	•	This alone is a daily touchpoint that keeps businesses engaged with your platform
Review Collection
	•	After booking completes → SMS to customer with one-time link
	•	One-time link = fills their name/rating/text, submits directly to your DB
	•	Shows on GCR profile AND their website
	•	Businesses pay for this because Google reviews are everything to them
	•	Key: make it one-tap, not a form — "Rate your experience: ⭐⭐⭐⭐⭐" as buttons
Last-Minute Promos
	•	Thursday 2pm: operator has 3 open spots for Saturday
	•	SMS to your platform → auto-posts a Special to GCR + their website + optional push notification to tourists who saved that business
	•	This is a retention hook — operator stays on platform because it fills their empty seats
Photo Updates via SMS
	•	Business texts a photo to your Twilio number
	•	Your webhook receives it, uploads to Supabase storage, attaches to their entity gallery + their website gallery
	•	One update, appears everywhere
	•	This removes the biggest friction — business owners don't want to log into dashboards

5. App Store / Developer Platform
Good long-term vision, but don't build it yet. What you're describing is essentially a plugin/module system:

Business subscribes to:
  ✅ Basic listing (free or $29/mo)
  + QR Menu Module ($19/mo)
  + Booking Module ($49/mo + %)
  + SMS Automations Pack ($39/mo)
  + Review Collection ($19/mo)
  + Analytics Dashboard ($29/mo)
The CyberCheck dashboard sidebar already works like this — each section is a module. The foundation is there. What makes it an "app store":
	1.	Modules can be toggled on/off per business
	2.	Third-party developers can submit modules (later)
	3.	Billing is per-module (Stripe subscriptions per feature)
Don't open it to external developers yet. Build 3-4 killer first-party modules, prove the model, then open APIs.

6. QR Menus
You already have the data for this. An entity with a grouped_items section for menu = you can generate a mobile-optimized QR menu page at:

gcr.app/menu/dockside-restaurant
That page is just a stripped-down version of the menu tab from profile.html. Business prints the QR code. Tourist scans it, sees live menu (updated whenever owner updates it in dashboard). You charge $19/mo for "digital QR menu." The data is already there — it's a 1-day build.

7. One Dashboard, Updates Everywhere — The Core Value Prop
This is the right message. When you pitch to businesses:
"You update your menu once. It updates your website, your GCR listing, your QR table menus, and your Google Business description draft — automatically."
That's the pitch. The technical architecture you already have supports this — entity sections drive the website template AND the GCR profile. The work is making sure that connection is tight and reliable.

function tagToPage(tag) {
  const key = tag.toLowerCase().replace(/-/g,'_');
  return TAG_TO_PAGE[key] || TAG_TO_PAGE[tag.toLowerCase()] || `search.html?q=${encodeURIComponent(tag)}`;
}

function tagLabel(tag) {
  return tag.replace(/_/g,' ').replace(/\b\w/g, l => l.toUpperCase());
}

function starsHtml(rating) {
  if (!rating) return '';
  const r = Math.round(rating * 2) / 2;
  const full = Math.floor(r);
  const half = r - full >= 0.5;
  return '★'.repeat(full) + (half ? '½' : '') + '☆'.repeat(5 - full - (half ? 1 : 0));
}

/* ── Filter cards already in the grid ── */
function applyFilter(grid, filter) {
  const cards = grid.querySelectorAll('.restaurant-card');
  let visible = 0;
  const norm = filter.toLowerCase().replace(/-/g,'_');
  cards.forEach(card => {
    if (filter === 'all') { card.style.display = ''; visible++; return; }
    const tags = (card.dataset.tags || '').split(',');
    const subtype = (card.dataset.subtype || '');
    const match = tags.some(t => t === norm || t.includes(norm)) || subtype.includes(norm);
    card.style.display = match ? '' : 'none';
    if (match) visible++;
  });
  const meta = document.querySelector('.toolbar-meta');
  if (meta) meta.textContent = `${visible} result${visible !== 1 ? 's' : ''}`;
}
