What you are actually building

You are building a destination data system, not just a website.

Gulf Coast Radar becomes:
	•	a public search engine
	•	a directory
	•	a business profile network
	•	a booking layer
	•	a local concierge
	•	a live information system
	•	a structured knowledge base for AI

CyberCheck becomes:
	•	the backend profile builder
	•	the business dashboard
	•	the editing system
	•	the CRM / automation / control layer

So the core job is this:

Every place, business, activity, unit, amenity, special, event, and local point of interest must be stored as structured data, so search, AI, filters, and concierge answers all work correctly.

⸻

The biggest rule

Do not think of this as pages first.

Think of it as:
	1.	Entity types
	2.	Relationships
	3.	Structured fields
	4.	Reusable page templates
	5.	Search/filter/tagging
	6.	AI generation + AI retrieval

If you structure the data right, the pages, dashboard, RAG, filters, and concierge all become easier.

If you structure it wrong, all of it becomes a mess.

⸻

The master architecture

You need 7 layers:
	1.	Location / hub layer
	2.	Business / property / place layer
	3.	Sub-entity layer
	4.	Content module layer
	5.	Taxonomy / tags / attributes layer
	6.	Availability / live-status layer
	7.	AI / search / retrieval layer

17. Where agents should live

You asked this earlier.

Best practical setup:
	•	main frontend / dashboard on Vercel
	•	agent API service separate from frontend
	•	database in Supabase or equivalent
	•	optional background jobs on AWS / Railway / Render / server environment better suited for longer tasks

Best structure
	•	app.yourdomain.com → dashboard
	•	gcr public site → consumer site
	•	api.yourdomain.com → app API
	•	agents.yourdomain.com → AI/agent orchestration service

Vercel is fine for frontend and light API work.
For heavier long-running AI workflows, scraping, scheduled jobs, and queue-based work, a separate backend service is cleaner.

19. Search / AI retrieval structure

Query pipeline

Step 1: identify intent

	•	hotel/condo search
	•	local info question
	•	event lookup

Step 2: extract filters

Example:
“live music, happy hour, gluten-free menu”

Filters become:
	•	live_music = true
	•	happy_hour = true
	•	gluten_free = true

Step 3: check categories and tags
	•	category = restaurant
	•	tags match the filters

Step 4: check structured child records
	•	happy hour records
	•	event records
	•	menu data
	•	availability

Step 5: ask follow-up if needed

Example:
	•	which area are you in?
	•	today or another date?
	•	adults / kids?

Step 6: rank results

By:
	•	exact match
	•	location
	•	availability
	•	freshness
	•	popularity
	•	review score

A category is not just a menu button on the site.
A category is a way of organizing the same business or place so users can find it from different angles.

That means a business does not belong to only one category.

Example:
Tee Off at The Wharf can be:
	•	a restaurant
	•	a thing to do
	•	a happy hour spot
	•	an indoor activity
	•	a family-friendly place

That is the whole power of your system.

So categories do 3 jobs at once:
	1.	they organize the site for users
	2.	they tell search where something belongs
	3.	they help AI understand what kind of result to return

⸻

The 3 levels of organization

To make this easy to understand, think of the platform in 3 layers:

1. Entity

This is the actual thing.

Examples:
	•	Cobalt
	•	Sunny Lady Dolphin Cruises
	•	Dockside Parasail
	•	The Wharf
	•	a condo
	•	a condo unit
	•	a beach access point

That is the real object.

2. Category

This is the section of the site it should appear in.

Examples:
	•	Restaurants
	•	Things To Do
	•	Happy Hour
	•	Specials
	•	Hotels
	•	Condos
	•	Shopping
	•	Events

3. Tags / attributes

These are the details that describe it more specifically.

Examples:
	•	gluten-free
	•	kid friendly
	•	waterfront
	•	indoor
	•	brunch
	•	live music
	•	hot tub
	•	sleeps 6

That is the search detail layer.

So:
	•	entity = what it is
	•	category = where it shows up
	•	tag = what makes it special

⸻

With categories, users can quickly find what they want.

For example:

Gulf Coast Radar: developer explanation

1. What Gulf Coast Radar is

Gulf Coast Radar is a consumer-facing local discovery, search, and booking platform for tourist-heavy coastal markets like Orange Beach, Gulf Shores, Fort Morgan, and similar destinations.

It is not just a directory.

It is a structured platform that lets users:
	•	discover restaurants, bars, coffee, sweets
	•	find happy hours and specials
	•	browse live music and events
	•	search things to do
	•	search lodging like hotels and condos
	•	search practical local info like beach access, parking, boat ramps
	•	eventually ask natural-language questions and get accurate results
	•	eventually book activities, lodging, or other experiences

The key difference is that the platform is built around structured data instead of static pages.

So the same source of truth should power:
	•	the business’s own page/site
	•	Gulf Coast Radar listing pages
	•	hub pages like The Wharf
	•	QR menus
	•	search results
	•	filters
	•	AI concierge / RAG responses
	•	future voice/TTS experiences

2. High-level product goal

The product goal is:

one update in the dashboard should update everywhere that entity appears

Example:

A restaurant updates:
	•	hours
	•	menu item
	•	happy hour
	•	special
	•	image

That update should flow to:
	•	their own hosted page/site
	•	their GCR business page
	•	category pages like Restaurants / Happy Hour / Specials
	•	hub pages like The Wharf
	•	QR menu page
	•	search results
	•	AI answers

So the architecture should be built around a central structured database, not page-level hardcoded content.

5. Important architecture rule

Do not model the system as “pages first.”

Model it as:
	1.	entity
	2.	classification
	3.	relationships
	4.	modules
	5.	structured child data
	6.	search / AI retrieval

13. Search and AI behavior

The AI should not answer from blobs of text only.

The query system should work like this:

Step 1: detect intent

Examples:
	•	restaurant search
	•	event lookup
	•	activity booking
	•	stay/lodging search
	•	local utility question

Step 2: extract filters

Examples:
“live music, happy hour, gluten-free menu”
becomes:
	•	live_music = true
	•	happy_hour = true
	•	gluten_free = true

Step 3: search structured data first

Use:
	•	categories
	•	tags
	•	menu data
	•	events
	•	specials
	•	schedules
	•	amenities
	•	availability
	•	relationships

Step 4: semantic layer second

Use embeddings/semantic search for softer concepts like:
	•	date night
	•	not too loud
	•	rainy day
	•	classy but casual
	•	family fun

Step 5: ask follow-up question if needed

Examples:
	•	what dates
	•	how old are the kids
	•	what area are you staying in
	•	indoor or outdoor

This is the future concierge behavior.

	•	menu items
	•	happy hour times
	•	event times
	•	unit bedrooms
	•	availability

Display data

This is presentation content.

Examples:
	•	About paragraph
	•	feature bullets
	•	FAQ answers
	•	visitor notes
	•	“perfect for” descriptions

This can live in flexible modules.

So the rule is:

if the system needs to query it, filter it, rank it, or answer questions from it, it should be structured.

If it is just supporting display copy, it can be flexible.
